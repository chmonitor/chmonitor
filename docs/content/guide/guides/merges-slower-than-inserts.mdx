`Code: 252. DB::Exception: Too many parts (N). Merges are processing significantly slower than inserts` is the same error as [Too many parts](/guide/guides/too-many-parts), but this page is for the other side of it: your **write rate has outpaced the background merge scheduler**, not that the insert pattern itself is wrong. If batching and partitioning already look sane, the bottleneck is merge capacity.

## Long-running or stalled?

A merge running for hours can still be healthy. **Long-running Merges**
(stable rule id `stuck-merges`) counts merges older than 10 minutes and stays a
warning signal. It sends no alert by default. **Stalled Merges**
(`stalled-merges`) becomes critical when an active merge has unchanged work
counters for `HEALTH_MERGE_STALL_SECONDS` (default 900 seconds).

Compare rows read/written, uncompressed bytes read/written and columns written
across observations of the same database, table and result part. An advancing
counter is work even when progress is at or above 1, as happens while a
vertical merge finishes columns. Progress changes also restart the flat window.
A first sample, counter decrease, elapsed reset or a different inferred start
time cannot establish a stall. Unchanged counters during a new observation
window remain unknown until the stall timeout; confirmed work advancement or
completion can resolve an existing alert.

The rule needs shared D1 or Postgres metadata storage. Samples are isolated by
endpoint and ClickHouse login, because permissions can hide other merges. Run sweeps at least
every 10 minutes. A gap over 15 minutes (the scheduled cadence plus jitter)
restarts the window. At that cadence, the default 15-minute stall becomes
detectable at the 20-minute observation. A successful complete query removes
finished merges. Missing storage, failed queries, malformed rows and failed
snapshot writes return unknown and cannot generate a recovery. Opening Active
Alerts or querying its findings through MCP only reads metadata; it never
writes samples or creates the sample table.

Run this read-only query twice and compare all work counters before treating
merge duration as a fault:

```sql
SELECT database, table, result_part_name, elapsed, progress,
       rows_read, rows_written, bytes_read_uncompressed,
       bytes_written_uncompressed, columns_written
FROM system.merges;
```

## Why it happens

<Mermaid chart={`flowchart TD
  Inserts["INSERT rate"] --> Queue["Part queue"]
  Pool["Merge pool + disk IOPS"] --> Merges["MergeParts"]
  Queue --> Race{"Merges keep up?"}
  Merges --> Race
  Race -->|"no"| Backlog["Code 252 / delay inserts"]
  Mut["Mutations"] -.-> Pool`} />

<Accordions>
<Accordion title="Undersized merge pool">

`background_pool_size` / `background_merge_scheduling_pool_size` too small for the sustained write rate — not enough worker threads to merge parts as fast as they arrive.

</Accordion>
<Accordion title="Slow disks">

Merges are I/O-heavy (read every source part, write the merged part). Network-attached storage without enough IOPS, or spinning disks under a high write rate, can't sustain it.

</Accordion>
<Accordion title="Very large parts">

`max_bytes_to_merge_at_max_space_in_pool` (default 150 GiB) lets merges grow large; a single big merge can occupy a worker for a long time and delay everything queued behind it.

</Accordion>
<Accordion title="Concurrent mutations">

`ALTER … UPDATE/DELETE` runs through the same merge pool and competes with regular merges for threads.

</Accordion>
<Accordion title="A single hot partition">

Serializes merges that could otherwise run in parallel across partitions.

</Accordion>
</Accordions>

## Diagnose

See what's merging right now, then look at the trend:

```sql
-- Active merges: what's running, how far along, how long it's taken
SELECT
    database,
    table,
    round(progress * 100, 2) AS pct_done,
    elapsed,
    is_mutation,
    formatReadableSize(total_size_bytes_compressed) AS merge_size
FROM system.merges
ORDER BY elapsed DESC;
```

```sql
-- Merge count and duration over the last hour — a rising queue means merges are losing ground
SELECT
    toStartOfMinute(event_time) AS minute,
    countIf(event_type = 'NewPart') AS parts_created,
    countIf(event_type = 'MergeParts') AS parts_merged
FROM system.part_log
WHERE event_time > now() - INTERVAL 1 HOUR
GROUP BY minute
ORDER BY minute;
```

`parts_created` consistently outrunning `parts_merged` confirms the backlog is on the merge side, not a one-off spike.

## Fix

<Steps>
<Step>
### Give merges more workers

Raise `background_pool_size` and `background_merge_scheduling_pool_size` in server config (requires a restart). This is the direct fix when the write rate is legitimate and merges just don't have enough threads.
</Step>
<Step>
### Move to faster storage

If `system.merges` shows long elapsed times relative to `merge_size`, merges are I/O-bound — local NVMe will outperform network-attached storage here by a wide margin.
</Step>
<Step>
### Reduce merge cost

Avoid partition keys that concentrate all writes into one huge partition (see [Too many parts](/guide/guides/too-many-parts)), and prefer codecs/compression settings that don't blow up merge CPU cost on every pass.
</Step>
<Step>
### Slow the insert side as a stop-gap

While merge capacity catches up, client-side batching buys time immediately. Raising `parts_to_delay_insert` throttles writes on purpose so merges can catch up — treat it as temporary, not a fix.
</Step>
</Steps>

<Callout type="info" title="This is the root cause behind too-many-parts">
If you landed here from a `Too many parts` error, this page is the deeper diagnostic — the insert-side fixes on that page (batching, partition key) only help if merges genuinely have spare capacity to catch up once inserts slow down.
</Callout>
